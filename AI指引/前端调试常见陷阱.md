# 前端调试经验

## 经验一：「点击无反应」先查事件是否真的触发了

"点击按钮没反应"和"点击按钮报了错"是两类问题。前者说明事件处理器根本没执行到。

**排查路径**：
1. 在事件处理函数第一行加 `console.log('触发了')`，看控制台有无输出
2. 如果没输出 → 事件绑定出了问题（内联 onclick 的变量未挂 window、addEventListener 未调用等）
3. 如果有输出但没后续 → 代码在某处静默抛异常，加 try-catch 打印

**本次案例**：`const QuizApp = {...}` 不挂 `window`，`onclick="QuizApp.xxx()"` 解析为 `null.xxx()`，TypeError 被内联事件机制吞掉，表现就是"完全无反应"。

## 经验二：「Failed to fetch」先区分是前端还是后端

"Failed to fetch" 是 fetch API 网络失败时的通用错误，不是"服务器返回了错误响应"。

**排查路径**：
1. 先用 curl/Postman 从命令行直接调 API → 确认后端是否存活
2. 如果命令行能通但浏览器不行 → CORS 或 HTTPS 混合内容问题
3. 如果命令行也不通 → Worker 没部署 / 路由不匹配 / 代码崩溃

**本次案例**：命令行能调通，但浏览器报 Failed to fetch。真正的问题是前端 `QuizApp` 为 null，根本没发出 fetch 请求——错误信息具有误导性。

## 经验三：「执行成功」不等于「生效了」

CLI 工具默认行为经常与预期不符，首次操作务必确认目标环境。

**排查路径**：
1. 执行任何写操作前，先确认操作的对象（本地/远程？开发/生产？）
2. 操作完成后，用读命令验证（`SELECT * FROM users` 看看表是否真的存在）
3. 不确定时加显式参数（`--remote`、`--prod`）

**本次案例**：`wrangler d1 execute --file schema.sql` 默默在本地执行，输出"10 commands executed successfully"极具欺骗性。直到 Worker 报 `no such table: users` 才发现加 `--remote`。

## 经验四：三层部署架构必有三种排错方向

p_easyQuiz 的架构是：**浏览器 → Pages(静态) → Workers(API) → D1(数据库)**。

一个"注册失败"可能断在任意一层：
1. **Pages 层**：JS 代码 bug，根本没发出请求
2. **Workers 层**：路由匹配失败、代码异常、CORS 拒绝
3. **D1 层**：表不存在、SQL 错误

**排查顺序**：从外到内逐层验证，每一层排除后再看下一层。不要跨层猜测。
